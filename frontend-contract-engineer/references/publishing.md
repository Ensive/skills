# Reading and publishing interfaces

Discover the content format, route conventions, publication/draft metadata, typography tokens and existing voice examples. Keep authored text byte-for-byte where possible during layout work; make editorial changes only when requested. Do not invent personal anecdotes, testimonials or case-study outcomes.

Prefer semantic `main`, `article`, headings, lists, links and labelled navigation. Preserve meaningful heading order and anchor IDs. Set readable line length and scalable typography using existing tokens, test long titles/URLs and code blocks, and keep focus/hover states visible. Prefer ordinary links over scripted navigation for static articles.

Preview drafts locally without making them publicly discoverable. Verify routes, metadata, feed/sitemap inclusion rules and canonical URLs when those are in scope. A missing CMS does not justify creating one for a spacing or typography change.

For a case study, separate problem, your contribution, implementation evidence, measured outcome and limitations. Use public or explicitly cleared artifacts; use generic/synthetic examples otherwise. The interface can present evidence without exposing customer code or inventing a business result.

Acceptance examples: article text is unchanged; headings/landmarks and skip link are present; long content does not overflow; navigation works by keyboard; drafts remain excluded from public output. HTML parsing alone does not prove contrast, zoom, visual layout or screen-reader usability.
